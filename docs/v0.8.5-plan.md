# v0.8.5 计划：Web / minitool 架构收敛与跨端质量

日期：2026-10-30
状态：架构审查与实施建议，尚未实施

## 1. 结论与审查范围

现有拆分方向合理，不建议重写或把两端合成一个应用。v0.8.0 已抽出共享 core、score-view、score-library；近期 minitool 的主要变化在阅读、操作和平台集成。技术债务主要集中在共享组件的跨端验证、双音频运行时的一致性、应用编排残留和发布追踪。

本次按当前工作区审查，包含尚未提交的 v0.8.1–v0.8.4 相关改动；不能把工作区实现等同于已发布版本。对照了 v0.8.0 计划、近期 progress、v0.8.3 计划、应用入口、共享包、音频适配器、测试与构建发布脚本。TODO 目前没有实际任务。

本计划只修改文档，不修改业务实现、版本号或发布状态。平台相关判断以代码和仓库验收记录为依据，未在本次重新核验在线平台契约，也未进行容器或真机验收；涉及桥接字段和支持版本的实施必须再次核实。

## 2. 已有架构及应保留的边界

```text
apps/web ───────┬─ core（Parser / Layout / Scheduler / Player）
               ├─ score-view（React SVG、跟随滚动）
               └─ score-library（JSONC 资源、生成与查询）
apps/minitool ─┴─ 同一组共享包

Web 音频：apps/web/src/adapters/audio → Tone.js / 采样与合成音
小工具音频：apps/minitool/src/adapters/audio → NativeTransport / Web Audio
平台桥接、页面状态、持久化：各应用负责
```

- `packages/core` 当前没有 Tone/React 运行依赖，Player 注入运行时；音乐语义已经共享，不应重复抽取另一套播放引擎。
- Web 的 `components/ScoreView/*` 主要是共享包转导出，`services/scoreLibrary.ts` 也是共享门面，不是两套独立实现。
- 两端共用同一曲库源文件与生成流程；`build-shared.mjs` 会生成资源、编译并运行曲库解析及调度校验。
- 根 CI 已覆盖 lint、共享构建、测试、两端构建、依赖边界与 minitool 静态审计；不能把“尚未建立 CI”列为新债务。
- 原生音频、离线 IIFE、相对路径资源和轻量合成音是小工具的平台适配；Web 保留编辑、个人曲谱、OCR、目录同步及钢琴采样具有合理性。

## 4. 功能是否需要同步

“共享音乐语义必须一致，产品交互按使用场景选择”应成为双端规则。以下是建议，不代表本版全部实施。

| 能力 | 当前差异 | 同步决策 |
| --- | --- | --- |
| 曲库、语法、奏法、歌词、双声部 | 已共享 | 修复和新增语义必须两端验收；无需再复制源码或建立同步脚本 |
| 跟随滚动修复 | 共享组件已更新，Web 也会使用 | 必须同步验证，特别是编辑器定位与跟谱的优先级 |
| 闲置恢复跟随 | minitool 设为 2000ms；Web 未开启 | Web 可提供显式选项或纯阅读模式启用；编辑模式保留手动控制，避免用户对照源码时被拉走 |
| 紧凑阅读、页内横向 | minitool 专用布局 | 建议 Web 后续增加独立“练习/阅读”视图，复用已有谱面与播放状态；勿直接旋转编辑器和全站布局 |
| 速度控制 | minitool 40–220 且夹取谱面默认速度；Web 节拍器滑块 40–240，另有 practiceSpeed | 本版先定义“谱面速度 / 实际播放速度 / 练习倍率”的契约，并验证范围边界。不要直接把小工具上限覆盖 Web；考虑合法谱面超过 220 时是否应静默改变初始速度 |
| 节拍猫与弧形速度选择 | minitool 新交互；Web 用原有控件 | 按需迁移为展示组件，保留键盘、精确输入与减少动态效果；不是架构修复的前置条件 |
| 节拍事件消费 | 两端均使用 Player 单一 `setBeatCallback`，Web Metronome 自行注册/清理 | 若同时显示多个节拍视图，应由应用统一订阅并下发；必要时扩展订阅 API，避免后注册者覆盖回调，不单独开启动画时钟 |
| 发笔记、关注作者 | minitool 平台能力 | 平台调用不迁入 Web；Web 可另做图片下载，优先复用谱面节选渲染能力 |
| 评论快照恢复 | v0.8.3 为计划；当前按钮是“发笔记” | 不列为已实现同步项。先确认快照接收契约，再单独实施；分享卡不等于可恢复链接 |
| 编辑、OCR、文件系统、钢琴采样 | Web 专有 | 保持差异，不为了功能数量对等搬入离线小工具 |
| 练习偏好 | 小工具最新需求为每次选曲重置；Web 有自己的编辑/练习状态 | 不统一持久化策略；统一状态名称和重置时机说明即可 |

## 5. 全局问题与补充建议

### 5.1 同一源码不代表用户运行同一版本

Web 可持续更新，小工具 ZIP 可能滞留在旧版本。共享包只解决源码复用，不能解决用户端版本偏差。建立每个产品的发布记录、兼容范围和回退产物；分享快照应带 schema 版本、稳定曲谱 ID，曲库重命名/下架需要回退提示。暂不承诺账号、个人曲谱或偏好跨端同步。

### 5.2 真机验收债务需要停止累积

v0.8.2 / v0.8.4 记录仍有容器与 Android/iOS 待验收；普通浏览器与 ZIP 静态审计都不能关闭这些项。发布前对同一 SHA-256 的候选 ZIP 验证安全区、方向切换、触摸、音画同步、后台/前台、分享成功/取消/失败。未完成则标记候选，不写“端到端完成”。

Web 当前 pagehide 处理主要负责编辑落盘，minitool 则主动停止播放，两者生命周期策略不同。先确定 Web 是否允许后台练习，再检查切页、锁屏、音频焦点丢失和返回页面的行为；不盲目统一成失焦即停止。

### 5.3 共享层不得被最低平台能力反向绑架

保留包级依赖边界，并逐步覆盖 core 内部 Parser/Renderer/Player 的方向。当前边界脚本主要阻止跨应用、共享包反向引用和平台包导入，并不完整验证内部层次。小工具兼容性审计应针对其实际产物；避免为了旧内核删除 Web 能力，也避免共享组件不经审计引入现代 API、全局 CSS 或平台桥接。

### 5.4 曲库增长、离线体积与授权信息

当前两端同用完整资源入口；曲库增大后，minitool 的离线首包、解析/布局耗时及复杂双声部 DOM 成本都会增加。先记录 ZIP/JS 字节数、首屏和长谱性能，再按数据决定构建期资源子集，仍保持一份源资源和稳定 ID。

资源模型已有 `attribution`，建议核查页面和分享卡是否正确展示署名与授权要求。公开分享会扩大曲谱传播范围；为资源增加可追溯的来源、授权及下架记录，在有传播限制时限制分享。这里是治理建议，未对现有曲谱作侵权判断。

### 5.5 防止过度抽象

本版不建设万能 Platform SDK、不把 Zustand store 搬进共享包、不抽整个 toolbar，也不复制 Web UI 到小工具。优先解决实际重复的语义、渲染编排与验收场景；只有两端确有消费者时再新增共享练习 UI 包。

## 6. 实施顺序与完成标准

1. **建立基线**：更新架构说明、能力矩阵和发布版本策略；给工作区实现、候选产物、平台验收、正式发布分别记录状态。
2. **清理与隔离**：移走 PracticePreference 类型、清理未启用持久化；补分享超时/竞态处理；补实际行为测试后再拆 minitool App。
3. **跨端可靠性**：Web 显式传播放状态；建立两套运行时契约场景及共享谱面的两端浏览器验收。播放行为修复先做，不夹带全面 UI 改版。
4. **发布收敛**：统一入口并补产品对应清单；新鲜 checkout 安装、共享构建、测试、两端构建、边界、审计、打包回读完整走通，确保不依赖开发目录旧 dist。
5. **完成容器验收**：对候选 ZIP 记录平台版本、设备、步骤和结果；保留失败证据和回退包。评论恢复、Web 阅读模式及共享导图按独立后续任务推进。

本版建议必须交付：P1 的清理和可靠性项、明确的同步策略、可追溯发布流程，以及实际容器验收记录。P2 和视觉升级不作为 v0.8.5 阻塞项。具体实现时应把每项拆成可独立审查的改动，不在一次重构中同时改播放器语义、状态结构和整体 UI。
