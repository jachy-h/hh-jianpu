# v0.7.8 计划：钢琴首次播放加载优化

日期：2026-10-28  
状态：方案阶段，尚未实施；基于当前工作区代码。

## 目标与现状

缩短点击播放到首音响起的等待，保持现有钢琴音色、循环持续段、响度和拍点契约。

当前 `apps/web/src/services/piano-samples.json` 注册 30 个采样，覆盖 A0–C8；本地 WAV 合计约 2.6 MB。`apps/web/src/adapters/audio/sample-instrument.ts` 每次创建音色库时把全部 URL 交给 `ToneAudioBuffers`，等待全部下载、解码完成才可发声。一次普通音域的旋律也要等待未使用的高低音采样。当前并非代码逐个串行下载，不能把“改成并行请求”作为主要优化。

`packages/core/src/player/synth.ts` 切换音色时销毁音色库，切回钢琴会重新建立缓冲；HTTP 缓存可以减少下载，但不能代替解码缓存。以上是代码确认的等待路径，网络、服务器响应和设备解码各占多少，仍需浏览器实测。

## 推荐方案

### 1. 按本次播放需要加载，保持原采样映射

- 从实际播放事件收集发声频率，包含双声部、装饰音、颤音和暂停/选段入口恢复的持续音；跳过休止、纯高亮事件。
- 复用现有“最近 MIDI 采样”选择规则，从完整清单确定每个音符的采样，再去重得到资源集合。等距时沿用原清单顺序，避免音色变化。
- 先做整曲所需采样；选段可作为后续优化，必须保证换选段时重新检查资源。不要只根据简谱数字或最低/最高音猜测采样。
- 在开始调度前准备完所需资源，播放回调只读取缓冲；不在 `noteOn` 中发请求，避免漏音和节奏抖动。
- 示例：C4 大调一个八度 C4–C5，按当前规则只需 C4、D#4、F#4、A4、C5 共 5 个采样，请求数比全量减少约 83%，WAV 文件量约 0.48 MB。这是资源规模估算，首音耗时改善以实测为准。
- 资源未齐时不能改用“已加载集合里的最近音”临时替代，否则同一首歌会随加载进度改变音色。

实现边界：core 只传递通用的发声准备信息，采样映射、URL 与加载均在 Web 音频适配器中处理。新增可选的准备能力或加载上下文，合成音使用空实现；保留现有调用兼容，不让 core 依赖 Tone.js 或钢琴清单。

### 2. 复用下载和解码结果

- 引入应用音频运行时范围的采样仓库，以带版本的资源 URL 和兼容的解码上下文参数作为缓存标识。
- 缓存进行中的 Promise，预取、播放和双声部共享同一次请求与解码；成功缓存 AudioBuffer，失败移除条目，允许重试。
- 音色切换只释放发声节点和音色实例对资源的引用；仓库保留可复用缓冲，避免切回钢琴又解码。
- 按解码后的实际大小管理内存，设置可配置预算，例如初始 16 MiB；LRU 只淘汰未被使用的条目。运行时销毁时统一清理，不能沿用音色库无条件销毁共享缓冲的方式。
- 静态资源路径加入内容 hash 或采样版本；检查实际部署的 Cache-Control 后配置长期缓存，避免“同 URL 改内容”产生旧资源问题。浏览器缓存可能被清理，冷启动仍须正常工作。

### 3. 提前准备，维持现有交互

- 编辑页曲谱解析成功且当前选择钢琴后，防抖预取所需文件；移动端弱网或省流量设置可跳过预取，点击播放仍正常加载。
- 预取优先下载字节；Tone.js 保持动态导入，音频上下文解锁继续由用户播放手势触发。提前解码作为后续实测优化，不依赖后台自动解锁音频。
- 曲谱编辑、移调或换谱时计算新资源集合，只补齐缺失资源。重复编辑不重复下载，限制预取并发并以实际测量调整。
- 加载进度沿用播放按钮内的固定尺寸状态和无障碍提示，不插入会令播放条横移的新文字控件。
- 停止、切谱和切换音色使旧播放意图失效；旧请求完成后可进入缓存，但不得自动开始播放或覆盖新状态。共享请求只在无消费者时取消。
- 失败/超时明确提示重试，并保留手动切换原声的入口；不在后台自动切换音色。

## 分期与取舍

| 优先级 | 工作 | 收益与限制 |
|---|---|---|
| P0 | 增加加载测量；整曲所需采样准备；共享 Promise 与解码缓存 | 直接减少首次等待，切回音色复用资源；跨全音域曲谱可能仍需全部采样 |
| P1 | 曲谱稳定后预取；资源版本与部署缓存；加载状态完善 | 把部分等待提前到阅读曲谱期间；刚进页立即播放仍走 P0 |
| 后续评估 | 无损资源压缩或少量分区包 | 测量请求延迟和传输占比后决定，避免提前增加资源制作复杂度 |

v0.7.8 不优先做全量大包：它减少请求数，但普通旋律仍须下载全音域，缓存粒度也更粗。也不直接换成有损 MP3/Opus：当前采样依赖精确循环点，需要重新验证编码延迟、接缝和跨浏览器解码结果；不应仅为减小体积冒持续音退化的风险。沿用现有 WAV，先缩小首播必须等待的资源集合。

## 验收与测量

记录点击播放、运行时就绪、资源下载/解码完成、首音计划时刻，以及请求数、传输量、解码缓存命中和内存占用。将预备拍单独计时，不能算作资源等待；首音计划时刻还需结合实际试听验证。

- 冷缓存：上述 C4–C5 示例仅请求对应 5 个 WAV；与全量加载基线在相同设备、相同网络限制下比较，目标首播等待中位数下降至少 50%，同时记录 P95。该比例是待验证目标，不是现有测量结论。
- 热缓存：同一运行时再次播放、钢琴切原声再切回，对已缓存资源新增下载和解码次数均为 0；刷新后的 HTTP 命中与重新解码分开记录。
- 边界：全音域曲谱、双声部、升降调、装饰音、颤音、选段从持续音中间进入和暂停恢复均无缺样、无错音；纯休止曲谱不下载钢琴采样。
- 竞态：加载时连续播放/停止、换谱、移调、切音色；旧任务不得启动播放。并发请求去重，失败可重试，缓存淘汰不影响活动声部。
- 音频：沿用 `apps/web/tests/audio-validation.html` 验证一拍/四拍长音、变速、循环、暂停恢复、双声部静音与跨音区响度；采样映射和 PCM 不变，实际试听无接缝或响度退化。
- 浏览器：桌面 Chrome、Safari 和移动端 Safari；验证冷启动、刷新缓存、弱网、请求失败及音频解锁。播放栏加载前后布局稳定。
- 实施后运行 `pnpm lint`、`pnpm build:core`、`pnpm test`、`pnpm build:web`，更新播放音色说明及相关帮助。
